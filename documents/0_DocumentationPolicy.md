# ドキュメント作成方針 (Documentation Policy)

## 1. 本方針の目的

本ドキュメントは、我々が開発するWebサービスにおいて、一貫性のある高品質なプロダクトを効率的に構築するための「ドキュメント・ドリブン開発」の指針を定義する。

ここで定義するドキュメント群は、単なる成果物（記録）ではなく、以下の役割を持つ「生きた設計図」である。

* **共通言語 (Ubiquitous Language):** 多様な背景を持つ開発者、ステークホルダー、AIエージェントが、共通の理解（コンテキスト）に基づいて協働するための基盤となる。
* **価値判断基準 (Why):** 「なぜ」この機能を作るのか、「なぜ」この設計を選ぶのかという意思決定の根拠を明確にし、判断のブレを防ぐ。
* **仕様と設計 (What & How):** プロダクトの振る舞いと技術的実装を明確に定義し、実装の品質と一貫性を担保する。

## 2. 基本原則 (Core Principles)

1.  **Docs as Code (コードとしてのドキュメント):**
    * ドキュメント（特にMarkdown, OpenAPI, ADRs）は、ソースコードと同じGitリポジトリでバージョン管理する。
    * ドキュメントの変更は、コードと同様にPull Request (PR) ベースでレビューされる。
2.  **Single Source of Truth (SSOT - 唯一の真実の情報源):**
    * 同じ情報を複数のドキュメントに重複して記述しない。例えば、API仕様はOpenAPIファイルがSSOTであり、他はそれを参照する。
    * ドキュメントの「インデックス（索引）」を明確にし、情報がどこにあるかを容易に発見できるようにする。
3.  **Why → What → How のトレーサビリティ:**
    * ドキュメントは「Why（なぜ作るのか）」から「What（何をどう振る舞うか）」、「How（どう実装するか）」へと一貫して紐づいている必要がある。

## 3. ドキュメント体系

開発プロセスを「Why（ビジョンと戦略）」「What（ドメインと振る舞い）」「How（アーキテクチャと実装）」の3つのフェーズに分け、それぞれ以下のドキュメントを定義する。

### Phase 1: The "Why" (ビジョンと戦略)

**目的:** プロダクトの存在理由、ビジネス価値、成功の定義を明確にする。

#### ドキュメント 1: PR-FAQ (Press Release - FAQ)

* **目的 (Why):** プロダクトが顧客に提供する「真の価値」を、顧客視点（Working Backwards）で定義する。すべての開発の「北極星」となる。
* **主な内容 (What):**
    * **プレスリリース (Press Release):** サービスローンチ時に発表する架空のプレスリリース。誰の、どんな問題を、どのように解決するのかを、顧客が理解できる言葉で記述する。
    * **内部 FAQ (Internal FAQ):** 経営陣や他部署から予想される質問と回答。（例: 「競合Aとの違いは？」「なぜ今なのか？」「マネタイズ戦略は？」）
    * **顧客 FAQ (Customer FAQ):** エンドユーザーから予想される質問と回答。（例: 「〇〇はできないのか？」「料金は？」「セキュリティは？」）
* **オーナー:** プロダクトマネージャー (PdM), プロジェクトオーナー
* **タイミング:** プロジェクトキックオフ時（最優先で作成）
* **こだわりポイント:**
    * 専門用語や内部用語を避け、徹底的に「顧客の言葉」でベネフィットを記述する。
    * FAQが、プロジェクトの潜在的なリスクや懸念事項を先回りして特定し、それに対する答え（または調査方針）を示せていること。
* **注意点 (アンチパターン):**
    * 「機能リスト」を書くことではない。機能がもたらす「結果（価値）」を書く。

#### ドキュメント 2: ビジネス要求定義 (BRD: Business Requirements Document)

* **目的 (Why):** PR-FAQで定義したビジョンを、具体的なビジネス目標とプロジェクトの「境界線」に落とし込む。
* **主な内容 (What):**
    * **プロジェクトの目的:** このプロジェクトで達成すべきビジネスゴール。
    * **スコープ (Scope):** このプロジェクトで「やること (In-Scope)」。
    * **ノンスコープ (Non-Goals):** このプロジェクトで「やらないこと (Out-of-Scope)」。これを明確にすることが極めて重要。
    * **主要なステークホルダー:** 意思決定者、主要な関係者、役割分担（RACIなど）。
    * **主要業績評価指標 (KPIs / OKRs):** プロダクトの成功を測定するための定量的・定性的な指標。（例: 「登録後3日以内のアクティブ化率 30%」）
* **オーナー:** PdM, ビジネスアナリスト
* **タイミング:** プロジェクト計画フェーズ
* **こだわりポイント:**
    * KPIがSMART（具体的、測定可能、達成可能、関連性があり、期限がある）な目標として設定されていること。
    * 「やらないこと（Non-Goals）」が、関係者間で明確に合意されていること。
* **注意点 (アンチパターン):**
    * 実現可能性を無視した「夢物語」になること。PR-FAQとの一貫性を保ちつつ、現実的なスコープを定義する。

### Phase 2: The "What" (ドメインと振る舞い)

**目的:** 「Why」で定義された価値を、具体的なサービス/機能の「振る舞い」と「語彙」に翻訳する。

#### ドキュメント 3: ユビキタス言語集 (Ubiquitous Language Dictionary)

* **目的 (Why):** ドメイン駆動設計 (DDD) の中核。開発者、PdM、AIエージェントが、ビジネスロジックについて一切の誤解なく会話するための「共通辞書」を定義する。
* **主な内容 (What):**
    * **用語:** プロジェクトで使われる重要な名詞、動詞。（例: 「ユーザー」「アカウント」「記事」「公開」「予約投稿」）
    * **厳密な定義:** その用語が何を意味し、何と異なるのか。（例: 「ユーザー」はサービスに登録した個人。「アカウント」は請求単位であり、複数のユーザーが紐づく。）
    * **ビジネスルール:** 用語に関連する不変のルール。（例: 「無料ユーザーは月5回まで『記事』を『公開』できる」）
* **オーナー:** チーム全員（PdMと開発者が共同でオーナーシップを持つ）
* **タイミング:** 開発初期から継続的に更新・参照
* **こだわりポイント:**
    * 「生きた辞書」であること。新しい概念が出たら即座に追加・修正し、常に最新の状態を保つ。
    * 定義が曖昧な言葉（例: 「データ」「情報」「処理」）や、安易な同義語（例: 「顧客」と「ユーザー」の混在）を排除する。
* **注意点 (アンチパターン):**
    * 開発者だけが理解できる技術用語（例: 「DB」「API」「テーブル」）をここに記述しない。あくまでドメイン（ビジネス）の言葉を定義する。

#### ドキュメント 4: ユーザーペルソナとジャーニーマップ

* **目的 (Why):** 「誰」のために作っているのかを具体化し、その「誰」がどのような体験（ジャーニー）を経て価値にたどり着くのかを視覚化する。
* **主な内容 (What):**
    * **ペルソナ (Persona):** ターゲットユーザーの具体的な人物像。属性、スキル、利用動機、フラストレーション（Pain Point）を定義する。
    * **ユーザージャーニーマップ (Journey Map):** ペルソナがサービスを認知し、利用を開始し、価値を享受し、離脱するまでの一連の体験を時系列でマッピングする。各ステップでの行動、思考、感情、タッチポイントを記述する。
* **オーナー:** PdM, UX/UIデザイナー
* **タイミング:** 機能設計の開始前
* **こだわりポイント:**
    * ペルソナが単なる属性（例: 30代男性）ではなく、具体的な「課題」と「動機」に基づいていること。
    * ジャーニーマップにおいて、特に「フラストレーション」や「離脱ポイント」が明確に特定され、それが機能仕様のインプットとなっていること。

#### ドキュメント 5: 機能仕様書 (ユーザーストーリー & BDDシナリオ)

* **目的 (Why):** ユーザーペルソナが体験する価値を、具体的な「機能」の振る舞いとして定義する。これは開発者が実装すべき仕様であり、テストの基準でもある。
* **主な内容 (What):**
    * **ユーザーストーリー:** 「[ペルソナ]として、[目的]のために、[機能]がしたい」という形式。
    * **受入基準 (Acceptance Criteria):** ストーリーが「完了」したとみなすための条件リスト。
    * **BDDシナリオ (Gherkin記法):**
        * Feature (機能): 機能の概要
        * Scenario (シナリオ): 具体的な利用シーン
        * Given (前提): シナリオ開始前の状態
        * When (実行): ユーザー（またはシステム）の操作
        * Then (結果): 期待される振る舞いや結果
* **オーナー:** PdM (作成), 開発者 (レビュー・詳細化)
* **タイミング:** 各スプリント/イテレーションの計画時
* **こだわりポイント:**
    * BDDシナリオが「実装の詳細（例: どのボタンをクリックする）」ではなく、「ユーザーから見た振る舞いの価値」を記述していること。
    * 正常系シナリオだけでなく、エッジケースや異常系シナリオ（例: 入力エラー、権限不足）も網羅されていること。
* **注意点 (アンチパターン):**
    * 巨大な「ユーザーストーリー」を作ること。ストーリーは1～3日程度で実装・テストできる単位（INVEST原則）に分割する。

### Phase 3: The "How" (アーキテクチャと実装)

**目的:** 「What」で定義された振る舞いを実現するための、技術的な構造、インターフェース、および意思決定を記録する。

#### ドキュメント 6: システムアーキテクチャ (C4 Model)

* **目的 (Why):** 複雑なシステム構成を、異なる視点（全体像から詳細まで）を持つすべての関係者が理解できるように、階層的に視覚化する。
* **主な内容 (What):**
    * Level 1: System Context (文脈): システム全体と、それに関わる外部システム（決済代行、認証基盤など）やユーザー（ペルソナ）との関係図。
      [C4モデルのコンテキスト図の例]
    * **Level 2: Containers (コンテナ):** システムを構成する主要な実行単位（例: Web App (React), API Gateway, 決済サービス (Microservice), メインDB (PostgreSQL)）の構成図と責務。
    * **Level 3: Components (コンポーネント):** 各コンテナ内部の主要なモジュールやコンポーネント（例: 認証コントローラ、決済サービス、レコメンドエンジン）の関係図と責務。
    * *(Level 4: Code は省略。コード自体がドキュメントとなる)*
* **オーナー:** Tech Lead (TL), アーキテクト
* **タイミング:** 初期設計時。大きな変更がある都度更新。
* **こだわりポイント:**
    * 「図」だけを置かない。各要素（コンテナ、コンポーネント）が「何の責務（Responsibility）を持つのか」を必ずテキストで補足説明すること。
    * C4の各レベル間（例: Level 2のコンテナとLevel 3のコンポーネント）で一貫性が保たれていること。
* **注意点 (アンチパターン):**
    * Level 3 (Component) を最初から細かく作り込みすぎること。まずはLevel 1, 2で全体像の合意を得ることが重要。

#### ドキュメント 7: API設計仕様書 (OpenAPI)

* **目的 (Why):** サーバーサイドとクライアントサイド（Web/App/AIエージェント）が円滑に連携するための「契約書」を定義する。
* **主な内容 (What):**
    * **OpenAPI (Swagger) 形式 (YAML/JSON):**
        * エンドポイント (Path) とHTTPメソッド (GET, POSTなど)
        * リクエストパラメータ (Path, Query, Body) のスキーマ
        * レスポンス (Success, Error) のスキーマとHTTPステータスコード
        * 認証・認可の方法（例: OAuth2, Bearer Token）
* **オーナー:** TL, サーバーサイド開発者
* **タイミング:** 実装開始前（APIファースト）
* **こだわりポイント:**
    * スキーマ定義（JSON Schema）が厳密であること。type: object だけで済ませず、各プロパティの型、必須/任意、フォーマット（例: date-time, email）を明記する。
    * **エラーレスポンスのスキーマが共通化・定義されていること**。（例: 400, 401, 403, 500 時にどのようなJSONが返るかが明確であること）
    * CIでLintや構文チェックを自動実行する。

#### ドキュメント 8: データモデル定義 (ER図 / スキーマ)

* **目的 (Why):** アプリケーションの「状態」を永続化するデータベースの構造を定義する。
* **主な内容 (What):**
    * 論理ER図: 主要なエンティティ（ユビキタス言語と対応）とリレーションシップ（1対多、多対多など）の視覚的な図。
      [ER図（エンティティ関連図）の例]
    * **物理スキーマ定義:**
        * テーブル名、カラム名
        * データ型、長さ、制約（NOT NULL, UNIQUE, FOREIGN KEY）
        * インデックス（Index）の定義と、その理由。
* **オーナー:** TL, サーバーサイド開発者
* **タイミング:** 機能実装と並行して作成・更新
* **こだわりポイント:**
    * 「なぜ」この正規化レベルを選んだのか、あるいは「なぜ」あえて非正規化したのか、その設計意図が補足されていること。
    * カラムのNULL許容性（Nullability）が厳密に検討されていること。（安易なNULL許容はバグの温床となる）
* **注意点 (アンチパターン):**
    * ER図が一度作成されて更新されない。スキーママイグレーションツール（例: Flyway, Alembic）と連携し、スキーマの変更がER図（またはスキーマ定義書）に反映される仕組みを検討する。

#### ドキュメント 9: アーキテクチャ決定記録 (ADRs: Architecture Decision Records)

* **目的 (Why):** 将来の「技術的負債」を防ぐため、「なぜ」そのアーキテクチャや技術（DB, フレームワーク, ライブラリ）を採用したのか（あるいは採用しなかったのか）という**意思決定のプロセスと論拠**を記録する。
* **主な内容 (What):**
    * **タイトル:** 決定事項（例: 「データベースとしてPostgreSQLを採用する」）
    * **ステータス:** 提案中 / 承認 / 却下 / 非推奨
    * **コンテキスト (Context):** どのような課題があり、何を決定する必要があったか。
    * **検討した選択肢 (Options):** 例: 1. PostgreSQL, 2. MySQL, 3. DynamoDB
    * **決定 (Decision) と論拠 (Rationale):** どの選択肢を採用したか。なぜそれを選んだのか（メリット、デメリット、トレードオフの比較）。
    * **結果 (Consequences):** この決定によるポジティブな影響とネガティブな影響（例: 「スケーラビリティは高いが、運用コストが増加する」「DynamoDBを棄却したため、特定のクエリパフォーマンスが課題になる可能性がある」）。
* **オーナー:** TL, シニア開発者
* **タイミング:** 重要な技術選定や設計変更が発生した都度
* **こだわりポイント:**
    * **「棄却した選択肢」とその「理由」**が必ず明記されていること。これが将来の「なぜアレを使わなかったんだっけ？」を防ぐ最も価値ある情報となる。
    * 軽量なMarkdownファイル（ADR-001.md, ADR-002.md ...）としてGit管理すること。

#### ドキュメント 10: 運用・監視設計書 (Operations & Monitoring)

* **目的 (Why):** サービスをリリースした後、安定稼働させ、問題発生時に迅速に対応するための「守り」の設計を定義する。
* **主な内容 (What):**
    * **SLI / SLO:** サービスレベル指標（例: レスポンスタイム、エラーレート）と目標値（例: 99.9%）の定義。
    * **監視 (Monitoring):** どのメトリクス（CPU, Memory, Latency）を、どのツール（例: Datadog, Prometheus）で監視するか。
    * **ロギング (Logging):** どのレベル（INFO, WARN, ERROR）のログを、どのようなフォーマット（JSON）で出力・収集するか。
    * **アラート (Alerting):** どのような閾値（例: エラーレートが5分間1%超）で、誰に（例: オンコール担当者）、どう通知（例: Slack, PagerDuty）するか。
    * **(簡易) Runbook:** 主要なアラート発生時の一次対応フロー。
* **オーナー:** TL, SRE, インフラ担当
* **タイミング:** リリース設計フェーズ
* **こだわりポイント:**
    * アラートが「対応可能（Actionable）」であること。「CPU使用率80%」といった曖昧なアラートではなく、「ユーザーに影響が出ている（または出そうな）事象」に基づいてアラートが設計されていること。
* **注意点 (アンチパターン):**
    * リリース直前に慌てて作成すること。監視やロギングは実装と同時に組み込むべき設計要素である。

## 4. ドキュメントの運用・保守

1.  **レビュープロセス (Docs as Code):**
    * すべてのドキュメント（特に Phase 2, 3）の新規作成・更新は、GitのPull Request (PR) を通じて行う。
    * PRでは、関連するステークホルダー（例: API仕様変更ならPdMとクライアント開発者）が必ずレビューを行う。
2.  **更新のトリガー:**
    * **機能開発時:** ユーザーストーリーの実装が完了した時点で、関連するドキュメント（API仕様書, データモデル, C4図など）が最新化されていることを「完了（Done）の定義」に含める。
    * **仕様変更時:** PdMがBRDや機能仕様書を変更した場合、その影響を受ける「What」と「How」のドキュメントオーナーに通知し、更新を依頼する。
3.  **陳腐化の防止:**
    * 定期的に（例: クォーターごと）ドキュメントの棚卸しレビューを実施する。
    * 古くなったドキュメントは、削除するか、「DEPRECATED（非推奨）」と明記する。
