# ドキュメント 8: アーキテクチャ決定記録 (ADRs)

## 1. 本書の目的

本書は、`0_DocumentationPolicy.md` に基づき、MVP（実用最小限の製品）開発における重要な技術的「意思決定」の背景、理由、およびその結果（トレードオフ）を記録します。

これにより、将来の技術的負債の発生を防ぎ、新しいチームメンバーへのコンテキスト共有を容易にすることを目的とします。

## 3. ADR 詳細

### ADR-001: MVPのモノリシック構成（Inertia.js）採用

* **ステータス:** Accepted

#### Context (背景)

* `1_proposal.md` (6.3) にて、MVP開発期間は「〜2週間」と定義されており、極めて迅速な開発が求められている。
* `1_proposal.md` (6.1) では、技術選定として `Laravel` + `Inertia.js` + `React` の構成が示唆されている。
* 将来的な構想として、AIエンジン（`FastAPI`）のマイクロサービス分離も言及されているが、これはMVPのスコープ外である。

#### Decision (決定)

* MVP開発フェーズにおいては、API（バックエンド）とフロントエンドを分離せず、`Inertia.js` を利用したモノリシック（密結合）アーキテクチャを採用する。

#### Rationale (論拠)

* **開発速度の最大化:** 従来のSPA + JSON API構成と比較し、APIのエンドポイント設計、スキーマ定義、認証（例: JWT/Sanctum）、CORS設定などの工数を大幅に削減できる。
* **型定義の不整合リスク低減:** `ドキュメント6 (ページプロパティ定義)` で定義されるPropsの「契約」に集中でき、バックエンド（リソースクラス）とフロントエンド（TypeScript型）の同期が比較的容易である。
* **チーム体制:** `1_proposal.md` (7.1) に記載の通り、現在は企画・開発を兼任する1名体制であり、責務が分離された複数チーム間での開発（API分離構成のメリット）は不要である。

#### Consequences (結果・影響)

* **メリット:** MVPのコア体験（`1_proposal.md` 6.3）の実装に最速で集中できる。
* **デメリット（トレードオフ）:**
    * 将来的にマイクロサービス化（`1_proposal.md` 6.1）や、Webフロントエンド以外のクライアント（例: スマートフォンアプリ）を開発する際には、APIを別途構築する必要があり、`Inertia.js` で実装したロジックの一部（コントローラやリソースクラス）は改修または再利用が困難になる可能性がある。

### ADR-002: PostGISの採用

* **ステータス:** Accepted

#### Context (背景)

* `1_proposal.md` (2.2) のコア体験フローにおいて、ユーザーは「出発地」を入力する。
* `1_proposal.md` (6.1) のデータ基盤構築戦略において、Step 3（スポットベースのクラスタ再構築）では、地理空間クエリ（例：特定の範囲内に存在するスポット群）の実行が必須となる。
* `2_DB_DesignDocument.md` (2. ER図) では、`spots` テーブルと `clusters` テーブルに `GEOGRAPHY` 型のカラムが定義されており、GiSTインデックスが必須とされている。

#### Decision (決定)

* データベースとして `PostgreSQL` を採用し、その標準的な拡張機能である `PostGIS` を利用する。

#### Rationale (論拠)

* **機能要件:** 「出発地からの距離計算」「特定範囲内のスポット検索」「スポット群の地理的中心（Centroid）の計算」など、本サービスのコア機能の多くが地理空間データ処理を必要とする。
* **技術的成熟度:** PostGISは、地理空間データを扱う上で最も機能豊富で成熟したオープンソース技術であり、`Laravel` (Eloquent) との連携ライブラリも存在する。
* **DBの統一:** 他のRDBMS機能（トランザクション、JSONBサポートなど）と地理空間機能を単一のデータベース（PostgreSQL）で完結でき、インフラの複雑性を低減できる。

#### Consequences (結果・影響)

* **メリット:** 複雑な地理空間クエリ（例: `ST_DWithin`, `ST_Centroid`）をSQLレイヤーで高速に実行できる。
* **デメリット（トレードオフ）:**
    * （`MySQL` などと比較して）PostgreSQL + PostGIS の運用・チューニングに関する学習コストがわずかに発生する。
    * `GEOGRAPHY` 型と `GiST` インデックスの特性を理解した上で、`spots.location` カラムを設計・運用する必要がある。
